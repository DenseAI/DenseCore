# Laya independent parity fixtures

These synthetic inputs exercise choice, score, noul, Unicode, a single option,
local attention beyond 128 tokens, the 512-token truncation boundary, reversed
option order, a 12-option question exercising temperature clamping, and a repeat
short request after the maximum-length request to check reusable scratch memory.
They are numerical compatibility tests, not task-accuracy or calibration claims.
`reference-parity.json` records the isolated build with GGML repacking and
llamafile disabled; `full-build-parity.json` records the normal full build with
those defaults enabled. Both pass the same nine cases and acceptance limits.
`parity-inputs.json` records tokenization and outputs from the independent
upstream PyTorch implementation, never values generated by DenseCore.

Pinned sources:

- GGUF: `zerodegress/laya-gguf`, revision
  `ff850ac9c08707e926847711a4d1819dc228ecc7`, `laya-f16.gguf`.
- Original weights/config: `convaiinnovations/laya`, revision
  `55cf4c4ebb4ebe31b2550e8bdf3bd21b99753851`, `model.safetensors`,
  `encoder/config.json`, and `rl_agent_config.json`.
- Original architecture/token construction: `NandhaKishorM/laya`, commit
  `6d942c92081fbc139e736bbd9ac0023223c29b7f`, `laya/common.py`.

`scripts/verify_laya_gguf.py` requires explicit local paths and
checks each input's SHA-256 before executing upstream code. No download or remote
code execution happens implicitly. Install torch, transformers, safetensors,
gguf, tokenizers, and numpy in a separate verification environment.

Example (replace paths to match the local artifacts):

```sh
python scripts/verify_laya_gguf.py \
  --gguf models/laya/laya-f16.gguf \
  --common /tmp/laya-pinned-common.py \
  --checkpoint /tmp/laya-upstream-model.safetensors \
  --encoder-config /tmp/laya-encoder-config.json \
  --agent-config /tmp/laya-agent-config.json \
  --library core/build/libdensecore_decision.so \
  --output /tmp/laya-parity.json \
  --fixtures-output benchmarks/fixtures/laya/parity-inputs.json
```

The harness verifies every learned GGUF tensor equals the upstream F16 tensor,
then executes both engines with FP32 arithmetic. Absolute-error limits are
`1e-3` for raw option logits and `1e-4` for calibrated probabilities. Act logits
use `abs(error) <= 1e-3 + 1e-6 * abs(reference)`, with a separate `1e-4` absolute
gate on act softmax probabilities. These limits are fixed in the script. Transformers uses eager attention and no autocast for the oracle.

Probability references follow the pinned upstream serving policy: option-count
buckets treat one option as `2`, and fitted temperatures are clamped to `[0.5, 5]`.
The original unmodified temperature metadata is checked independently against the
checkpoint configuration before this policy is applied.

`act-numeric-diagnostics.json` preserves the initial strict act-only `1e-3`
failures and PyTorch thread-count sensitivity. Act logits have magnitude about
4000; independent PyTorch 1-thread versus 4-thread runs differ by up to
0.0009765625. Native F32 differed by up to 0.00390625 (maximum 12 ULP across
both act coordinates, relative error below 1e-6). The act-only relative allowance
was introduced explicitly after this diagnostic; option/probability gates were
not changed. Initial native F16 activation arithmetic also failed option and
probability gates, so native projections were changed to FP32 arithmetic instead
of relaxing those gates. These cases have saturated act softmax distributions;
passing them does not establish act calibration on a broader distribution.

The Go boundary also has an opt-in integration gate, covering ordered JSON,
question rendering, exact token IDs and marker positions, native logits,
calibrated typed outputs, and the HTTP handler against these same fixtures:

```sh
cd server
DENSECORE_LAYA_MODEL=/absolute/path/to/laya-f16.gguf \
  go test -mod=readonly ./internal/decision -run TestNativeUpstreamParity -v
```

Build `libdensecore_decision` first. If it is outside the default `build/`
location, supply `CGO_LDFLAGS='-L/path/to/library -Wl,-rpath,/path/to/library'`.
Without `DENSECORE_LAYA_MODEL`, only the model-dependent integration test skips;
normal schema, serialization, tokenizer, probability, and HTTP tests still run.
